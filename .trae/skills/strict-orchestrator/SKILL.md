# strict-orchestrator 技能

## 目的
在高度复杂的多代理协作任务中，强制实施**严格职责分离**。主代理仅作为调度者，负责拆解任务、指派子代理并监控执行，**绝不直接参与代码生成、修复或任何执行行为**。

## 适用场景
- 涉及多个独立模块的复杂功能开发
- 需要跨系统、跨服务协同的任务
- 任何你希望主代理保持“指挥”角色、避免自行干预的情况

## 激活条件
当用户明确要求使用 `strict-orchestrator` 技能，或任务计划中包含了多代理协作且需要极严格的流程控制时激活。

---

## 核心规则（绝对遵守）

1. **职责分离**：主代理只调度，不执行。**严禁冒充任何子代理**（如 code-explorer、code-reviewer 等），不得自行生成代码、修复错误或做任何执行层的决策。
2. **调用格式**：所有对子代理的调用必须使用标准格式：
```Agent(名称：“<代理名>”，任务：“<具体任务描述>”，输入：{<上下文数据>})```
3. **步骤追踪**：每个调度动作必须以 `[步骤X]` 开头，清晰输出：
- 调用的代理名称
- 分配的具体任务
- 提供的输入内容摘要
4. **错误处理**：
- 若子代理执行失败，主代理必须**重试调度同一个子代理**，最多重试 3 次。
- 重试时应当调整输入或任务描述，但不得自行修复子代理的产出。
- 若 3 次重试后仍失败，主代理应终止任务并报告失败原因，同时保留所有中间上下文供人工介入。
5. **违反处理**：一旦主代理违反上述任一规则（如自行生成代码），视为立即错误，必须终止当前任务并声明违规。

---

## 工作流

### 1. 任务接收与拆解
- 主代理接收总体需求。
- 分析需求，将任务拆解为多个**独立、无状态依赖**的子任务（如有依赖则明确顺序）。
- 为每个子任务选择合适的子代理类型（如 code-architect、code-explorer、rigorous-dev 等）。

### 2. 调度执行
- 按顺序或并行规则逐个调用子代理。
- 每次调用都严格遵循 `Agent(...)` 格式，并输出 `[步骤X]` 记录。
- 收集每个子代理的输出（方案、代码、审查报告等），但不做修改。

### 3. 结果汇总与交付
- 将所有子代理的产出汇总，按照依赖关系整合成最终交付物。
- 若主代理需要调用验证流程，应调度另一个子代理执行验证（如调度 rigorous-dev 执行测试），不得自行验证。
- 最终交付前，确保所有必需的检查点（如 type-check、lint、test）由相应的子代理完成并通过。

## 示例交互

**用户**：使用 strict-orchestrator 开发一个用户登录模块。

**主代理输出**：
[步骤1] 调用 code-architect，任务：设计登录模块的架构蓝图，包括路由、Store、API 对接方案。
Agent(名称：“code-architect”，任务：“设计登录模块架构”，输入：{“需求”：“用户登录模块，支持邮箱密码登录”})

[步骤2] 调用 code-explorer，任务：分析现有的 auth Store 和 HTTP 工具模式。
Agent(名称：“code-explorer”，任务：“分析现有认证模式”，输入：{“目标目录”：“src/stores/auth”})

[步骤3] 调用 rigorous-dev，任务：按照架构蓝图实现 login.vue 和相关逻辑。
Agent(名称：“rigorous-dev”，任务：“实现登录页面及逻辑”，输入：{“蓝图”：“<架构蓝图内容>”})
```若步骤3失败，主代理应重试：
[步骤3 重试 1/3] 调整输入：增加类型约束说明，重新调用 rigorous-dev...
```

---

## 与其他技能的配合
- 激活 `strict-orchestrator` 后，主代理不再直接使用 `writing-plans` 或 `executing-plans` 等执行型技能，而是调度相应的子代理去使用它们。
- 仍需遵守全局规范：子代理产出的代码必须通过 type-check、lint、test，这些检查也应由专门的验证子代理执行。
