# 系统架构设计

> vue-assetmanagement 前端分层架构、模块职责、依赖规则与状态管理规范
> 适用于方案设计、架构调整、Store 开发

## 1. 架构总览

本项目采用 **前后端分离** 分层架构，前端独立部署，后端仅提供 API。前端内部按职责划分为清晰层次，遵循单向依赖、单向数据流，确保可维护性与扩展性。

┌─────────────────────────────────┐  
│ 视图层 (Views) │  
├─────────────────────────────────┤  
│ 组件层 (Components) │  
├─────────────────────────────────┤  
│ 业务逻辑层 (Composables / Services) │  
├─────────────────────────────────┤  
│ 状态管理层 (Stores) │  
├─────────────────────────────────┤  
│ 数据访问层 (Api / Utils) │  
└─────────────────────────────────┘

## 2. 目录职责与分层

| 目录                 | 层次    | 职责说明                                        |
| ------------------ | ----- | ------------------------------------------- |
| `src/views/`       | 视图层   | 路由页面，组合组件与业务逻辑，不直接操作 Store 或 API            |
| `src/components/`  | 组件层   | 可复用 UI 组件，纯渲染，复杂逻辑上抛 composables            |
| `src/composables/` | 逻辑层   | 可复用逻辑抽离（如表格配置、图表数据生成），无状态跨组件共享              |
| `src/services/`    | 服务层   | 业务核心流程（如资产状态流转校验），可调用 API 和 Store，不包含 UI 逻辑 |
| `src/stores/`      | 状态层   | 全局状态管理（Pinia），单一业务域，仅通过 action 修改状态         |
| `src/api/`         | 数据访问层 | 封装 HTTP 请求，按业务模块组织，**禁止业务逻辑**               |
| `src/utils/`       | 工具层   | 纯函数工具（如格式化、校验器），零依赖，可被任意层使用                 |
| `src/router/`      | 路由配置  | 路由表、守卫，基于权限动态加载                             |
| `src/types/`       | 类型定义  | 全局类型、接口，被所有层共享                              |
| `src/directives/`  | 指令    | 自定义指令（如 `v-can` 权限指令），直接操作 DOM              |
| `src/assets/`      | 资源    | 样式变量、图片等，不包含可执行代码                           |

## 3. 依赖规则（强制红线）

- **单向依赖**：上层可依赖下层，下层严禁依赖上层。  
  - 视图 -> 组件/服务/Store -> API/Utils
- **禁止跨层调用**：  
  - 视图不能直接调 API（必须通过服务层或 Store）
  - 组件不能直接调 Store（通过 props/emits 或父容器传递）
- **禁止循环依赖**：任何模块间不得形成循环引用。
- **类型依赖**：所有层依赖 `src/types/`，类型定义本身不得反向依赖业务代码。

## 4. 数据流规范

采用 **单向数据流** 模型，确保状态可预测：

- **全局状态**：Store 驱动，组件通过 `computed` 读取，通过 Store 的 action 触发变更，action 内部调用 API，组件绝不直接修改 Store 状态。

- **组件内部状态**：使用 `ref/reactive` 维护，通过 `provide/inject` 或 props/emits 实现父子通信。

- **服务层中介**：复杂业务逻辑（如资产流转需要多个 API 协调）封装在 `services/` 中，由 Store 的 action 调用服务，避免 Store 臃肿。
  
  用户操作 → 组件触发 → Store Action (或服务) → API 请求 → 更新 Store 状态 → 组件自动渲染

## 5. 状态管理（Pinia）

- **Store 设计原则**：
  - 组合式 Store：`defineStore + setup()`，内部使用 Composition API。
  - 单一职责：一个 Store 只管理一个业务领域（如 `asset`、`auth`、`app`）。
  - 持久化：需要本地持久化的状态（如 token）启用 `persist: true`。
- **使用约束**：
  - Store 状态在组件中只读（通过 `storeToRefs` 解构）。    
  - 异步操作（API 调用）在 Store 的 action 中完成，禁止在 action 外部直接修改 state。
  - 禁止在 Store 中引入 UI 逻辑（如 `ElMessage`），错误处理统一由 UI 层或拦截器完成。

## 6. 路由与权限架构

- **路由分层**：  
  - 公共路由（登录、404）  
  - 动态路由：登录后根据权限从后端获取并 `addRoute`。
- **权限控制点**：
  - 路由守卫：验证 Token、加载权限。
  - 指令级：`v-can` 基于 `@casl/ability` 控制按钮/组件显示。
  - 服务级：`services/` 中可二次校验权限，避免绕过 UI 直接调用。

## 7. 模块划分（业务域）

- `auth`：登录、Token 管理、权限加载

- `asset`：资产核心信息、入库、领用、外借、报废、回收

- `report`：报表、数据可视化

- `system`：用户管理、角色配置、字典维护
  
  各业务域在 `api/`、`stores/`、`components/` 中相对独立，共享类型定义和工具函数。

## 8. 技术实现约定

- **UI 组件**：Element Plus 按需引入，复杂表格使用 `vxe-grid`，图表使用 `v-chart`。
- **请求库**：统一使用封装的 `src/utils/request.ts`，自动注入 Token、统一错误拦截。
- **图标**：基于 `unplugin-icons` 自动注册，使用 `<icon-ep-xxx />` 形式。
- **类型安全**：API 返回数据必须定义 response 类型，避免前端猜测。

## 9. 开发与新需求接入

  当进行方案设计或架构调整时：

1. 检查当前分层是否符合上述依赖规则，严禁新增层级破坏单向流。

2. 新功能优先考虑：`api/` 封装请求 → `stores/` 或 `services/` 处理业务 → `components/` 纯渲染 → `views/` 组装。

3. 公共能力（如文件导出、表单校验）应下沉到 `composables/` 或 `utils/`，避免在组件中重复实现。
   
   > 所有设计决策均需符合 `AGENTS.md` 的红线规则与 Harness 流程，变更后同步更新本文件。
